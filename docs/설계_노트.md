# 설계 노트

과제 목표 5가지(B6-2-G1~G5)에 대한 답을 코드 근거와 함께 정리한다.
"이렇게 하는 게 좋다"가 아니라 **이 저장소가 실제로 그렇게 되어 있는 지점**을 가리킨다.

---

## 1. AI API 를 REST 로 연동하는 전체 흐름 (G1)

`POST /v1/messages` 하나로 끝난다. SDK 를 쓰더라도 아래 세 단계는 그대로다.

### 요청 구성 — [`client.ClaudeGenerator.generate`](../aigitgen/client.py)

```python
kwargs = {
    "model":  self.params.model,          # 어떤 모델
    "max_tokens": self.params.max_tokens, # 응답 길이 상한
    "system": system,                     # 역할·규칙 (매 호출 동일)
    "messages": [{"role": "user", "content": user}],  # 이번 변경 사항
    "output_config": {"format": schema},  # 응답 형식을 JSON 스키마로 고정
}
if self.params.sends_temperature:                      # sampling 지원 모델일 때만
    kwargs["extra_body"] = {"temperature": ...}        # SDK 시그니처에 없다 → 3절
```

`system` 과 `messages` 를 나누는 이유가 있다. **`system` 은 매번 같고 `messages` 만 바뀐다.**
바뀌지 않는 것을 앞에 두는 구조라 나중에 프롬프트 캐싱을 붙일 때 그대로 쓸 수 있다.

### 응답 처리

응답은 문자열이 아니라 **콘텐츠 블록의 배열**이다. `type` 을 확인하고 꺼내야 한다.

```python
for block in response.content:
    if getattr(block, "type", None) == "text":
        text = block.text
        break
```

그다음 `stop_reason` 을 반드시 본다. HTTP 200 이어도 정상 완료가 아닐 수 있다.

| `stop_reason` | 뜻 | 이 도구의 처리 |
| --- | --- | --- |
| `end_turn` | 정상 완료 | JSON 파싱 진행 |
| `max_tokens` | **응답이 잘림** | `--max-tokens` 를 올리라는 오류 |
| `refusal` | 모델이 거절 | 거절 사유를 담아 오류 |

`max_tokens` 로 잘린 응답을 그냥 파싱하면 "JSON 이 깨졌다"는 엉뚱한 오류가 난다.
원인이 아니라 증상을 보고하는 셈이라, 원인 단계에서 끊는다.

### 예외 대응

SDK 예외를 **좁은 것부터** 잡는다. 하나로 뭉뚱그리면 "재시도하면 되는 오류"와
"고쳐야 하는 오류"를 구분할 수 없다.

| 예외 | 사용자에게 보이는 안내 |
| --- | --- |
| `AuthenticationError` | API Key 를 확인하세요 |
| `PermissionDeniedError` | 이 키에 권한이 없습니다 |
| `NotFoundError` | `--model` 값을 확인하세요 |
| `RateLimitError` | `retry-after` 헤더의 시간 뒤 재시도 |
| `BadRequestError` | 요청이 거부됐습니다(400) + 원문 |
| `APIConnectionError` | 네트워크 상태를 확인하세요 |
| `APIStatusError` | 5xx 면 서버 오류, 그 외는 API 오류 |

전부 [`ApiCallError`](../aigitgen/errors.py) 로 바꿔 던지고, CLI 최상단에서 `[ERROR]` 한 줄로 출력한다.
스택트레이스는 `--debug` 를 붙였을 때만 나온다. **평상시에 사용자가 볼 것은 원인 한 줄이다.**

재시도는 직접 구현하지 않았다. SDK 가 연결 오류·408·409·429·5xx 를 지수 백오프로 2회까지
자동 재시도한다. 그 위에 내 재시도를 얹으면 요청 횟수가 조용히 곱해진다.

## 2. `temperature` 와 `max_tokens` 가 결과에 주는 영향 (G2)

| 파라미터 | 무엇을 바꾸나 | 이 도구의 기본값과 이유 |
| --- | --- | --- |
| `temperature` | 다음 토큰을 고를 때의 **무작위성**. 0 에 가까울수록 같은 입력에 같은 출력 | **0.2** — 커밋 메시지는 창의성보다 **일관성**이 중요하다. 같은 diff 에 매번 다른 요약이 나오면 리뷰가 어렵다 |
| `max_tokens` | 응답 **길이 상한**. 넘으면 문장 중간에서 잘린다 | **2000** — 커밋 1건 + PR 본문이 넉넉히 들어가는 크기. 더 키우면 비용만 늘고 결과는 길어지기만 한다 |

실험해 보려면 `--temperature 0.9` 로 두 번 돌려 결과를 비교하면 된다.
문장 표현이 눈에 띄게 흔들리는 대신, 요약이 diff 에서 멀어지는 것도 같이 보인다.

`max_tokens` 는 **비용의 상한이지 목표치가 아니다.** 출력 토큰만 과금되므로,
짧게 답하면 짧게 과금된다. 그래서 상한은 넉넉히 두고 길이는 **프롬프트로** 조인다
(제목 50자, 불릿 1~2개). 상한으로 길이를 조절하려 하면 문장이 잘린 채 반환된다.

### 최신 모델에서는 `temperature` 를 못 쓴다

`claude-opus-5`, `claude-sonnet-5`, `claude-opus-4-8` 등은 sampling 파라미터를 받지 않는다
(보내면 400). 이 도구는 그런 모델 목록을 [`client.SAMPLING_UNSUPPORTED`](../aigitgen/client.py) 로 갖고 있고,
해당 모델이 선택되면 `temperature` 를 빼고 호출하면서 경고를 남긴다.

기본 모델을 `claude-sonnet-4-6` 으로 잡은 이유가 이것이다.
**`--temperature` 가 실제로 동작하는 모델이어야** 파라미터 실험을 할 수 있다.

### `extra_body` 로 보내는 이유

`anthropic` 1.x 의 `messages.create()` 시그니처에는 `temperature` / `top_p` / `top_k` 가
**아예 없다.** 최신 세대 모델이 거부하도록 바뀌면서 SDK 의 타입 정의에서도 빠졌다.

```python
>>> sorted(inspect.signature(client.messages.create).parameters)
['cache_control', 'container', 'extra_body', ..., 'max_tokens', 'messages',
 'model', 'output_config', ..., 'system', 'thinking', ...]
```

하지만 REST API 자체는 sampling 지원 모델에 대해 `temperature` 를 여전히 받는다.
그래서 SDK 가 요청 JSON 에 병합해 주는 `extra_body` 로 넘긴다.

```python
kwargs["extra_body"] = {"temperature": self.params.temperature}
```

이게 실제로 본문에 실리는지는 짐작이 아니라 **테스트로 확인**한다.
[`tests/test_client_wire.py`](../tests/test_client_wire.py) 가 로컬 HTTP 서버를 띄우고
`base_url` 을 그쪽으로 돌려 SDK 가 보낸 JSON 을 그대로 받아 검사한다 —
sonnet-4-6 이면 `temperature` 가 있고, opus-5 면 없다.

## 3. Git 명령 결과를 프로그램 입력으로 연결하기 (G3)

[`gitctx.run_git`](../aigitgen/gitctx.py) 하나로 모든 git 실행을 통과시킨다.
분산시키지 않은 이유는 세 가지다.

1. **파싱 가능한 형식을 고른다.** 화면용 `git status` 대신 `git status --porcelain=v1` 을 쓴다.
   앞 두 글자가 스테이지/작업트리 상태이고 3번째 칸부터 경로라, 로케일이나 색상 설정에 흔들리지 않는다.
2. **실패를 예외로 바꾼다.** `returncode != 0` 이면 stderr 첫 줄을 담아 `GitError` 를 던진다.
   빈 문자열을 정상값으로 착각해 그대로 흘려보내는 사고를 막는다.
3. **상한을 둔다.** 30초 타임아웃. 거대한 저장소에서 도구가 멈춘 것처럼 보이지 않게 한다.

### 어떤 diff 를 모을 것인가

| 상황 | 실행하는 명령 |
| --- | --- |
| 기본 | `git diff HEAD` — 스테이지 + 미스테이지 전부 |
| `--staged` | `git diff --cached` — 스테이지된 것만 |
| 최초 커밋 전(HEAD 없음) | `git diff --cached` 로 내려감 |

실행한 명령을 `ctx.diff_command` 에 담아 **로그와 프롬프트에 그대로 노출**한다.
"무엇을 근거로 요약했는가"를 사용자가 확인할 수 있어야 하기 때문이다.

**추적되지 않은 파일은 내용을 넣지 않는다.** `git diff` 에 잡히지 않는 것이 원래 동작인데,
편의를 위해 파일을 읽어 넣기 시작하면 `.env` 같은 파일이 통째로 프롬프트에 실린다.
이름만 넣고, 그 사실을 프롬프트에 명시한다.

## 4. 프롬프트를 어떻게 구성했는가 (G4)

[`prompts.py`](../aigitgen/prompts.py) 의 설계 원칙 4가지.

### (1) 역할과 입력 계약을 먼저 못박는다

`system` 에 역할·금지사항·형식 규칙을 두고, `user` 에는 이번 변경 사항만 넣는다.
둘을 섞으면 "규칙"과 "데이터"의 경계가 흐려져, diff 안의 문장이 지시처럼 읽힐 수 있다.

### (2) 출력 형식을 문장이 아니라 JSON 스키마로 강제한다

`output_config.format` 에 스키마를 준다. "이런 형식으로 답해줘"라고 부탁하는 대신
**구조가 어긋날 수 없게** 만든다.

```python
"body_bullets": {"type": "array", "items": {"type": "string"},
                 "minItems": 1, "maxItems": 2},
"files_mentioned": {"type": "array", "items": {"type": "string"},
                    "minItems": 1, "maxItems": 3},
```

과제가 요구한 "본문에 파일 1~3개 언급 또는 핵심 변경 1~2개 불릿"이 스키마의 `minItems`/`maxItems`
로 그대로 들어가 있다. PR 쪽은 `why` / `what` / `how_to_test` 가 `required` 라
**세 섹션이 빠진 응답 자체가 나올 수 없다.**

### (3) 규칙은 숫자로 준다

"짧게" 가 아니라 "50자 이내를 목표로, 72자를 절대 넘지 않는다".
그리고 **그 숫자는 검증기가 쓰는 숫자와 같은 곳에서 온다** — `conv.commit.title_max`.
프롬프트에는 72자를 적어 놓고 검증기는 80자로 재는 식의 어긋남이 생기지 않는다.

### (4) 없는 사실을 만들지 못하게 한다

```text
- diff 에서 확인되지 않는 사실을 지어내지 않는다. 확실하지 않으면 파일 이름 수준으로만 쓴다.
- 「«MASKED:...»」 로 가려진 값은 민감정보다. 그 값 자체를 추측하거나 언급하지 않는다.
- diff 가 "생략" 표시로 잘려 있으면, 잘린 부분을 상상해 채우지 않는다.
```

마스킹과 잘라내기를 하는 도구이므로, **모델이 보는 입력에는 구멍이 있다.**
그 구멍을 상상으로 메우면 커밋 메시지가 사실과 달라진다. 구멍의 존재를 프롬프트에 명시하고,
얼마나 잘렸는지도 함께 알려준다(`민감정보 2건이 치환됨 / 파일 3개가 생략됨`).

`--show-prompt` 로 실제 전송 페이로드를 언제든 눈으로 볼 수 있다.
프롬프트를 고치고 결과가 어떻게 달라지는지 확인하는 것이 이 과제의 핵심이라, 숨기지 않았다.

## 5. 왜 검증하고 다듬는가 (G5)

모델은 "대체로" 규칙을 지킨다. 실무에서 문제가 되는 것은 그 "대체로"다.
제목이 80자로 나오는 일이 20번에 한 번이라도, **그 한 번이 커밋 히스토리에 영원히 남는다.**

이 도구는 세 겹으로 막는다.

| 단계 | 하는 일 | 비용 |
| --- | --- | --- |
| 1. 스키마 강제 | 구조가 어긋난 응답 자체를 막음 | 0 (요청에 포함) |
| 2. 검증 후 재생성 | 위반 목록을 붙여 **1회** 다시 요청 | API 호출 1회 추가 |
| 3. 후처리 | 남은 위반을 코드로 보정 | 0 |

과제는 2번과 3번 중 **하나만** 요구하지만 둘 다 넣었다. 이유가 다르다.
**재생성은 품질을 지키고, 후처리는 형식을 보장한다.**
재생성만 있으면 두 번째 응답도 어기면 방법이 없고, 후처리만 있으면 잘려나간 제목이 남는다.

### 재생성이 무한 루프가 되지 않는 이유

`MAX_API_CALLS = 2` 이고 재생성은 최대 1회다. 과제 제약("1회 실행 시 1~2회 이내")이
상수 하나로 코드에 박혀 있다. 게다가 **재생성 결과가 더 나쁘면 첫 결과를 쓴다.**

```python
if len(retry_problems) > len(problems):
    return draft, problems, True
```

### 후처리가 거짓말하지 않는 이유

빈 칸을 채울 때 쓰는 문장은 전부 **Git 에서 직접 읽은 사실**이다
([`polish._filler_pool`](../aigitgen/polish.py)).

```python
f"변경 파일 {len(ctx.relevant_files)}개: {names}"
f"diff {ctx.diff_lines}줄"
f"대상 브랜치: {ctx.branch}"
```

"성능이 개선되었습니다" 같은 문장은 만들지 않는다. 그건 diff 를 보고 판단할 일이지
빈 칸을 메우려고 지어낼 일이 아니다. 그리고 후처리를 했다면 **무엇을 고쳤는지 전부 출력한다.**

```text
[WARN] 후처리 2건을 적용했습니다.
       - 제목을 72자 이내로 줄임
       - 'What' 섹션 불릿을 Git 사실로 1개 보충
```

사용자가 "내가 검토해야 할 곳"을 바로 알 수 있어야, 초안이 초안으로 취급된다.

## 6. 구조를 왜 이렇게 나눴는가

```text
cli.py ──▶ gitctx.py    (git 실행)
       ──▶ redact.py    (안전 모드)
       ──▶ prompts.py   (프롬프트 조립)
       ──▶ client.py    (AI API 호출)
       ──▶ polish.py    (검증·후처리)
       ──▶ render.py    (출력)
```

의존은 한 방향이다. `client.py` 는 git 을 모르고, `gitctx.py` 는 AI 를 모른다.

### Git 수집과 AI 호출을 분리한 이유

**바뀌는 속도가 다르다.** `git status` 의 출력 형식은 십 년째 그대로지만,
AI API 는 파라미터 이름이 몇 달 만에 바뀐다(실제로 이 프로젝트에서
`temperature` 가 SDK 시그니처에서 사라지는 일을 겪었다 — 2절).
둘을 한 함수에 두면 API 가 바뀔 때마다 git 수집 코드까지 흔들린다.

**테스트 비용도 다르다.** git 수집은 임시 저장소만 만들면 공짜로 테스트되지만,
AI 호출은 키와 네트워크와 돈이 든다. 경계가 있어야 `FakeGenerator` 하나로
나머지 전부를 키 없이 테스트할 수 있다. 실제로 106개 테스트 중 8개만 SDK 를 요구한다.

### 프롬프트와 출력 검증을 분리한 이유

같은 규칙을 **두 번, 다른 방식으로** 써야 하기 때문이다.
프롬프트는 "72자를 넘지 마라"라고 **부탁**하고, 검증기는 "72자를 넘었나"를 **측정**한다.
부탁과 측정은 성격이 달라서 한 곳에 두면 둘 다 어중간해진다.

핵심은 **숫자의 출처를 하나로 묶은 것**이다. 둘 다 `conv.commit.title_max` 를 읽는다.
그래서 `.ai-gitgen.json` 에서 60 으로 바꾸면 프롬프트와 검증기가 **같이** 바뀐다.
분리하되 어긋나지 않게 하는 것이 요점이다.

### API 파라미터를 CLI 옵션으로 만든 이유

**재현성과 실험 용이성**이다.

- 코드에 박아 두면 값을 바꿀 때마다 파일을 고쳐야 하고, 그 기록은 남지 않는다.
- 옵션이면 실행 명령 자체가 기록이 된다.
  `python main.py commit --temperature 0.7 --model claude-haiku-4-5` 를 그대로
  트러블슈팅 노트에 붙일 수 있다.
- 값이 매번 로그에 찍힌다 — `[INFO] AI API 요청 중... (model=... temperature=0.2 max_tokens=2000)`.
  결과가 이상할 때 "어떤 설정으로 뽑았더라"를 되짚을 수 있다.

### `--dry-run` 을 넣은 이유

프롬프트를 고치는 작업은 반복이 많다. 매번 API 를 부르면 **돈과 시간이 반복 비용이 된다.**
`--dry-run` 은 AI 호출만 빼고 나머지 전 구간(수집 → 마스킹 → 프롬프트 조립 → 검증 → 후처리 → 출력)을
그대로 지난다. 형식 문제는 여기서 대부분 잡힌다.

## 7. 실무에 적용한다면

### 왜 생성 결과를 바로 쓰면 안 되는가

1. **모델은 diff 만 본다.** 왜 그 변경이 필요했는지는 diff 에 없다.
   `- retries=3` 을 보고 "재시도 횟수를 3으로 설정"이라고는 쓸 수 있어도,
   "결제 게이트웨이 장애 대응"이라고는 쓸 수 없다. Why 는 사람 머릿속에만 있다.
2. **안전 모드가 입력에 구멍을 낸다.** 마스킹·잘라내기를 거친 diff 는 원본이 아니다.
   생략된 파일에 핵심 변경이 있었다면 요약이 통째로 빗나간다.
3. **커밋 메시지는 지워지지 않는다.** 틀린 요약은 히스토리에 영구히 남아,
   나중에 `git log` 로 원인을 찾는 사람을 잘못된 곳으로 보낸다.

그래서 이 도구는 **초안 텍스트를 출력하는 데서 끝난다.** 커밋도, push 도 하지 않는다.
후처리를 한 경우에는 무엇을 고쳤는지 `[WARN]` 으로 전부 보여준다 —
사용자가 어디를 봐야 하는지 알려주기 위해서다.

### 팀에 붙인다면 무엇부터

| 순위 | 추가할 것 | 왜 먼저인가 |
| --- | --- | --- |
| 1 | **커밋 이력 기반 컨벤션 자동 추론** | 지금은 `.ai-gitgen.json` 을 사람이 쓴다. 최근 커밋 100개를 읽어 prefix·스코프 패턴을 뽑아내면 팀이 설정 파일을 안 써도 자기 스타일이 나온다. **도입 장벽이 채택률을 결정한다** |
| 2 | **이슈/티켓 번호 연결** | Why 를 채우는 유일한 자동 경로다. 브랜치 이름의 `PROJ-123` 을 읽어 이슈 제목을 컨텍스트로 넘기면, 모델이 지어내던 배경을 사실로 바꿀 수 있다 |
| 3 | **프롬프트 캐싱** | 시스템 프롬프트는 매 호출 동일하다. 캐시를 붙이면 입력 토큰 비용이 크게 준다. 팀 규모에서 호출 수가 곱해지므로 여기서부터 비용이 보인다 |
| 4 | **git hook 연동** (`prepare-commit-msg`) | 편의는 크지만 **가장 나중이다.** 자동으로 끼어드는 도구는 품질이 확실해진 뒤에 붙여야 한다. 초안이 부실한 채로 hook 에 걸면 팀이 도구를 꺼 버린다 |

순서의 기준은 **"틀린 요약이 나올 확률을 줄이는 것"이 먼저, "손이 덜 가게 하는 것"이 나중**이다.
편해지기만 하고 정확도가 그대로면, 사람들은 결국 검토를 건너뛴다.

## 8. `temperature` / `max_tokens` 를 직접 실험해 보기

체크리스트가 요구하는 "값을 바꿔 실행했을 때 차이가 재현되는가"를 확인하는 절차다.
**API Key 가 필요하다.**

```bash
export ANTHROPIC_API_KEY="sk-ant-..."

# 같은 변경에 대해 temperature 만 바꿔 두 번씩
python main.py commit --temperature 0.0 > /tmp/t00-a.txt
python main.py commit --temperature 0.0 > /tmp/t00-b.txt
python main.py commit --temperature 1.0 > /tmp/t10-a.txt
python main.py commit --temperature 1.0 > /tmp/t10-b.txt

diff /tmp/t00-a.txt /tmp/t00-b.txt    # 0.0 → 거의 같다
diff /tmp/t10-a.txt /tmp/t10-b.txt    # 1.0 → 표현이 눈에 띄게 흔들린다
```

```bash
# max_tokens 를 조이면 어떻게 되는가
python main.py pr --max-tokens 2000    # 정상
python main.py pr --max-tokens 100     # [ERROR] 응답이 max_tokens 에서 잘렸습니다.
```

두 번째가 중요하다. `max_tokens` 를 줄이면 **답이 짧아지는 게 아니라 잘린다.**
그래서 길이는 `max_tokens` 가 아니라 프롬프트의 글자 수 규칙으로 조인다(2절).
잘린 응답을 그냥 파싱하지 않고 원인을 짚어 주는 것도 이 때문이다.

## 9. 나중에 메운 두 구멍

둘 다 "요구사항은 충족인데 실행 단계에서 조용했던" 지점이다.
기록해 두는 이유는 고쳤다는 자랑이 아니라, **두 번 다 같은 모양의 실수**였기 때문이다 —
규칙을 문서와 프롬프트에만 적고, 실행되는 검사로 옮기지 않았다.

### (1) "50자 권장" 이 런타임에서 사라졌던 것

R5-2 는 두 숫자를 준다 — **50자 이내 권장, 최대 72자.**
처음 구현은 72자만 검증했고, 50자는 프롬프트 문장(`prompts.py`)으로만 존재했다.
모델이 66자 제목을 주면 프로그램은 아무 말 없이 통과시켰다. 명세의 절반이 실행되지 않았다.

지금은 두 숫자가 **서로 다른 처리**를 받는다.

| 길이 | 판정 | 누가 처리하나 | 결과 |
| --- | --- | --- | --- |
| ~50자 | 권장 충족 | — | 조용 |
| 51~72자 | 권장 초과 · 상한 이내 | `polish.advise_commit()` | `[WARN]` 한 줄. **자르지 않는다** |
| 73자~ | 상한 위반 | `polish.validate_commit()` → `_fit_title()` | 재생성 트리거 + 절삭 |

**왜 `validate_commit()` 에 합치지 않았나.** 합치면 51자 제목이 '형식 위반'이 되어
재생성을 부른다. 한 번 실행 1~2회라는 호출 제약(C1-2)을 권장선 때문에 쓰는 셈이다.
**권고는 돈을 쓰지 않고 사용자에게만 말해야 한다.** 그래서 검증(재생성을 부르는 것)과
권고(부르지 않는 것)를 다른 함수로 나눴다.

경계값과 "절삭 대신 경고"라는 성질은 `tests/test_polish.py::TestTitleAdvice` 와
`tests/test_cli.py::TestTitleRecommendation` 이 고정한다 —
50자는 조용하고, 51자는 경고하고, 66자 제목은 **66자 그대로 출력되는지**까지 잰다.

### (2) 로그와 산출물이 같은 스트림으로 나갔던 것

`[INFO]/[WARN]/[DONE]` 이 stdout 으로 나가서, `python main.py commit > msg.txt` 가
로그까지 파일에 담았다. 화면에서는 멀쩡해 보이므로 눈으로는 영영 안 보이는 결함이다.

지금은 **로그는 stderr, 산출물은 stdout** 이다(`render._log` / `render._emit`).
터미널에서 보이는 모습은 그대로고, 달라지는 것은 리다이렉트할 때다.

```bash
python main.py commit > msg.txt     # msg.txt 에는 초안만 남는다
python main.py commit 2> /dev/null  # 초안만 보고 싶을 때
bash demo.sh                        # 샘플은 2>&1 로 합쳐 캡처하므로 예전 그대로다
```

8절의 `temperature` 실험 절차가 이 분리의 덕을 직접 본다. `diff /tmp/t00-a.txt
/tmp/t10-a.txt` 가 **모델 출력의 차이만** 보여준다. 예전에는 저장소 경로와 파일 수 같은
로그가 같은 파일에 섞여 있었다.

`tests/test_cli.py::TestStreamSeparation` 이 stdout 에 `[INFO]`·`[DONE]` 이 없는지,
그리고 실패했을 때 stdout 이 **비어 있는지**를 검사한다. 실패했는데 stdout 에
무언가 남으면 파이프가 쓰레기를 받는다.
