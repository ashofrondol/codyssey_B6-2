# AI 커밋/PR 자동 생성기

`git status` / `git diff` 결과를 읽어 **커밋 메시지**와 **Pull Request 초안**을
Claude API 로 만들어 터미널에 출력하는 CLI 도구. 코디세이 B6-2 미션 산출물이다.

핵심은 API 를 "부르는 것"이 아니라 **무엇을 입력으로 주고, 결과를 어떻게 검증하느냐**다.
이 저장소는 그 두 가지에 대부분의 코드를 쓴다 — [프롬프트 설계](aigitgen/prompts.py),
[안전 모드](aigitgen/redact.py), [형식 검증과 다듬기](aigitgen/polish.py).

- **개발 환경**: Python 3.10 이상 / 터미널 전용 (웹 화면 없음)
- **외부 의존성**: 공식 `anthropic` SDK 하나 (그 외는 전부 표준 라이브러리)
- **기본 모델**: `claude-sonnet-4-6` — `--temperature` 가 **실제로 동작하는** 모델을 기본값으로 뒀다
  (Opus 5 / Sonnet 5 등 최신 세대는 sampling 파라미터를 거부한다. 자세한 이유는 [설계 노트 2절](docs/설계_노트.md))
- **1회 실행 API 호출**: 기본 1회, 형식 위반 시 재생성 포함 **최대 2회**

#### 원문 — 1. 미션 소개

> AI API 연동이라고 하면 거창하게 들리는데, 사실 핵심은 '어떤 입력을 주냐'에 있습니다. git diff를 넘기고, 의미 있는 커밋 메시지와 PR 설명이 나오게 프롬프트를 설계하는 것이 이번 미션입니다. 단순 API 호출이 아니라, AI 결과물의 품질을 직접 제어하는 방법을 경험합니다.
>
> AI API는 외부 AI 모델의 텍스트 생성 기능을 애플리케이션에서 호출해 사용할 수 있게 해주는 방식입니다. 고객 응대 문장 생성, 문서 요약, 개발 로그 정리처럼 입력값을 받아 AI가 생성 결과를 반환하는 자동화 작업에 활용됩니다.
>
> 이번 미션에서는 AI API를 호출하는 Python 코드를 기반으로, Git 변경 사항을 입력값으로 받아 커밋 메시지와 PR 설명을 자동 생성하는 CLI 도구를 개발합니다. 단순 호출에 그치지 않고, API 파라미터와 컨텍스트(Commit/PR 양식, 변경 이유, 요구사항)를 설계해 원하는 품질의 결과가 나오도록 프롬프트를 최적화합니다.
>
> 또한 Git 명령 실행 결과를 프로그램에 연결하고, 생성된 결과물을 실제 커밋/PR 작성 흐름에 적용하며 연동·검증·자동화를 하나의 흐름으로 구현합니다. 이를 통해 AI 기능을 서비스에 붙이는 방식을 구현 관점에서 이해하고, 이후 다양한 업무 자동화/개발 보조 도구로 확장할 수 있는 기반을 갖추게 됩니다.

> 💡 **(해설) 이 과제가 진짜로 묻는 것**
> 1. **"API를 호출할 줄 아느냐"가 아니라 "출력 품질을 통제할 줄 아느냐"를 묻는다.** `requests.post()` 한 줄은 이 과제의 5%다. 나머지 95%는 *무엇을 프롬프트에 넣을지(컨텍스트 설계)* 와 *나온 결과가 규칙을 어겼을 때 어떻게 할지(검증·후처리·재생성)* 이다.
> 2. **비결정적(non-deterministic) 출력을 결정적(deterministic) 계약으로 만드는 훈련이다.** LLM은 "커밋 제목 50자"를 지키지 않을 수 있다. 그래도 내 프로그램은 항상 50자 이내를 내놔야 한다 → 이 간극을 메우는 레이어를 직접 만들어 보라는 것.
> 3. **외부 시스템 3개를 파이프로 잇는 통합 연습이다.** `git`(subprocess) → 내 프로그램(프롬프트 조립) → AI API(HTTP) → 다시 터미널. 각 경계에서 실패(변경 없음, 키 없음, 네트워크 오류)가 어떻게 전파되는지 설계해야 한다.
> 4. **비용과 보안이 처음으로 실물이 되는 과제다.** 호출 1회 = 실제 돈, diff 전송 = 실제 유출 가능성. "1~2회 제한", "safe-mode 마스킹"이 요구사항에 박혀 있는 이유다.
> 5. **AI 결과를 그대로 믿지 않는 태도**를 요구한다. 원문이 못 박는다 — *"생성된 커밋/PR 문구는 최종 정답이 아니며, 사용자가 검토 후 적용한다."*

### 0.2 최종 산출물 (제출물)

#### 원문 — 2. 최종 결과물

> 다음 3가지 결과물을 완성한다.

**1. AI API 연동 및 자동화 흐름 동작 확인**

- **입력/요청**: AI API Key를 환경변수로 설정한 뒤, 프로젝트 루트 디렉토리에서 커밋/PR 자동 생성을 수행하는 Python CLI 프로그램을 실행한다.
- **출력/화면**: Python이 `git status`, `git diff` 결과를 수집해 AI API를 호출하고, 변경 요약·커밋 메시지·PR 초안이 터미널에 출력된다. 사용자는 단일 실행으로 자동화 흐름이 끝까지 동작함을 확인할 수 있다.

**2. GitHub 리포지토리**

- **입력/요청**: GitHub에 리포지토리를 생성하고, AI 기반 Git 커밋/PR 자동 생성기 프로젝트(소스 코드 폴더)를 원격 저장소에 push 한다.
- **출력/화면**: GitHub 리포지토리에서 소스 코드/파일 구조가 정상적으로 업로드되어 있으며, 커밋 히스토리와 브랜치 작업 흐름을 확인할 수 있다.

**3. 사용 가이드 문서(README.md)**

- **입력/요청**: 리포지토리의 README.md를 열어 실행 방법을 확인한다.
- **출력/화면**: 설치 방법, 환경변수(API Key) 설정 방법, 실행 예시, 커밋/PR 생성 결과 예시, 주의사항(또는 운영 관점)이 포함되어 있어 사용자는 문서만 보고 도구를 실행할 수 있다.

#### 제출 증거 체크리스트 (원문 항목 정리)

- [ ] 단일 실행으로 `git status` 수집 → `git diff` 수집 → AI API 호출 → 커밋 메시지/PR 초안 출력까지 끝까지 동작하는 화면
- [ ] GitHub 리포지토리 URL (소스 코드 폴더 push 완료, 커밋 히스토리 + 브랜치 작업 흐름 확인 가능)
- [ ] README.md — 설치 방법 / 환경변수(API Key) 설정 방법 / 실행 예시 / 커밋·PR 생성 결과 예시 / 주의사항(또는 운영 관점)
- [ ] (보너스 선택 시) B1 제출 증빙: PR 링크 1개 + "AI 초안 → 최종 PR" 변경점 요약본 (5~10줄)
- [ ] (보너스 선택 시) B2 제출 증빙: 컨벤션 문서(README 섹션) + 컨벤션 적용 전/후 생성 결과 비교 1회
- [ ] (보너스 선택 시) B3 제출 증빙: safe-mode 정책(숫자 기준 포함) + safe-mode ON/OFF 결과 차이 비교

### 0.3 과제 목표 — 수료 후 스스로 설명할 수 있어야 하는 것

#### 원문 — 3. 과제 목표

> 이 과제를 마친 후, 학습자는 아래를 스스로 설명할 수 있어야 한다.

1. AI API를 REST API 방식으로 연동하는 과정에서 **요청을 구성하고, 응답을 처리하며, 예외를 대응하는 전체 흐름**을 말로 설명할 수 있다.
2. `temperature`, `max_tokens` 등 **주요 파라미터가 결과 품질에 어떤 영향을 주는지** 구분하고 설명할 수 있다.
3. `git status`, `git diff` 등 **Git 명령 실행 결과를 프로그램 입력으로 연결하는 방식과 자동화 흐름**을 설명할 수 있다.
4. **Commit/Pull Request 양식과 코드 변경 맥락을 포함해 AI가 요구사항에 맞는 요약을 생성하도록 프롬프트를 구성하는 원리**를 설명할 수 있다.
5. 생성된 커밋/PR 텍스트가 **실무 규칙(길이·템플릿·표현 제한)을 만족하도록 내용을 검증하고 필요한 부분을 다듬는 이유와 방법**을 설명할 수 있다.

### 0.4 기능 요구 사항 (필수)

#### 원문 — 4. 기능 요구 사항

> 다음 요구사항을 모두 만족해야 한다.

#### R1. Git 변경 사항 수집

- [ ] **R1** — Git 변경 사항 수집 기능을 구현한다.
  - [ ] **R1-1** — CLI 실행은 **Git이 초기화된 프로젝트 루트 디렉토리**에서 수행되어야 한다.
  - [ ] **R1-2** — CLI 실행 시 `git status` 결과를 수집하여 **변경된 파일 목록**을 확인할 수 있어야 한다.
  - [ ] **R1-3** — CLI 실행 시 `git diff` 결과를 수집하여 **변경 내용(diff 텍스트)** 을 얻을 수 있어야 한다.
  - [ ] **R1-4** — 변경 사항이 없을 경우, **"변경 사항이 없습니다"에 준하는 메시지를 출력하고 종료**해야 한다.

> 💡 (해설) R1-4는 "출력하고 **종료**" 다. 즉 AI API를 호출하지 않고 빠져나와야 한다 — 비용 0원. 원문 결과 예시의 문구는 `[INFO] 변경 사항이 없습니다. 커밋 메시지를 생성하지 않고 종료합니다.` 이다. (종료 코드가 0인지 1인지는 원문에 명시되어 있지 않다.)

#### R2. AI API 연동

- [ ] **R2** — AI API 연동을 구현한다.
  - [ ] **R2-1** — AI API Key는 **환경변수로 설정**되어야 하며, **코드에 하드코딩하지 않는다.**
  - [ ] **R2-2** — CLI를 실행하면 AI API가 호출되고, 생성된 **커밋 메시지 또는 PR 초안 텍스트가 터미널에 출력**되어야 한다.
  - [ ] **R2-3** — **API 호출 실패(네트워크 오류, 인증 실패 등) 시 오류 원인을 포함한 메시지**를 출력해야 한다.
  - [ ] **R2-4** — API 호출 파라미터(예: **모델, temperature, max_tokens**)는 **CLI 옵션으로 변경 가능**해야 한다.
    - 예: `-model`, `-temperature`, `-max-tokens` 같은 옵션을 제공하고 **기본값을 둔다.**

> 💡 (해설) PDF 텍스트에는 옵션이 하이픈 1개(`-model`, `-temperature`, `-max-tokens`)로 표기되어 있다. 원본 문서의 마크다운/PDF 변환 과정에서 `--`가 `-`로 축약되었을 가능성이 높다(같은 문서 안에서 `-safe-mode`도 동일 패턴). **구현 시에는 `--model / --temperature / --max-tokens` (GNU 롱옵션)로 두되, 채점자가 원문 그대로 입력할 수 있도록 하이픈 1개 형태도 함께 받아들이면 가장 안전하다.** 이건 추론이며 PDF에 명시된 바는 아니다.

#### R3. 커밋 메시지 자동 생성

- [ ] **R3** — 커밋 메시지 자동 생성 기능을 구현한다.
  - [ ] **R3-1** — `commit` 명령을 실행하면 커밋 메시지가 생성되어 **터미널에 출력**되어야 한다.
  - [ ] **R3-2** — 커밋 메시지는 **변경 사항 요약을 기반으로** 생성되어야 한다.
  - [ ] **R3-3** — 출력 결과에는 **커밋 제목 1줄이 필수**로 포함되어야 한다.
  - [ ] **R3-4** — 커밋 본문은 **선택적으로** 포함될 수 있다(본문 포함 여부는 구현 선택).
  - [ ] **R3-5** — **(요약 품질 최소 기준)** 커밋 본문을 포함하는 경우, 본문에 아래 중 **1개 이상**을 포함해야 한다.
    - 변경된 파일(또는 모듈) **1~3개** 언급
    - 핵심 변경 사항 **1~2개**를 불릿으로 요약
  - [ ] **R3-6** — 생성된 커밋 메시지는 터미널에 출력되어 **사용자가 복사하여 적용**할 수 있어야 한다.

#### R4. Pull Request 제목/본문 자동 생성

- [ ] **R4** — PR 제목/본문 자동 생성 기능을 구현한다.
  - [ ] **R4-1** — CLI 실행 시, **PR 제목/본문 초안을 생성하는 명령어**를 실행할 수 있어야 한다.
  - [ ] **R4-2** — PR 본문은 **템플릿 구조**를 가져야 하며 아래 **섹션 헤더를 포함**해야 한다.

    ```
    Why(변경 배경)
    What(핵심 변경 사항)
    How to Test(테스트 방법)
    ```

  - [ ] **R4-3** — **각 섹션에는 최소 1개 이상의 불릿**이 포함되어야 한다.
  - [ ] **R4-4** — **PR 제목은 1줄**로 출력되어야 하며, **PR 본문과 함께 터미널에서 확인**할 수 있어야 한다.

#### R5. 출력 형식 검증 및 다듬기

- [ ] **R5** — 생성된 커밋/PR 텍스트는 아래 길이/형식 규칙을 적용할 수 있어야 한다(**검증 후 재생성 또는 후처리 중 택1**).
  - [ ] **R5-1** — 규칙 적용 방식을 **"검증 후 재생성"** 또는 **"후처리"** 중 하나로 선택해 구현한다.
  - [ ] **R5-2** — **커밋 제목: 50자 이내 권장(최대 72자)**
  - [ ] **R5-3** — **PR 제목: 최대 80자**
  - [ ] **R5-4** — **PR 본문: Why/What/How to Test 섹션 헤더 필수 + 각 섹션 최소 1개 불릿**
  - [ ] **R5-5** — 사용자가 결과를 검토할 수 있도록, **최종 출력은 구분선/헤더 등으로 구획이 나뉘어** 표시되어야 한다.

| 대상 | 규칙 | 원문 표현 |
| --- | --- | --- |
| 커밋 제목 | 50자 이내 **권장**, **최대 72자** | "커밋 제목: 50자 이내 권장(최대 72자)" |
| PR 제목 | **최대 80자** | "PR 제목: 최대 80자" |

### 0.6 개발 환경 · 제약 사항

#### 원문 — 6. 개발 환경

- **Python 3.10 이상**
- **웹 화면 없이, 터미널에서 실행되는 프로그램으로 구현한다.**

#### 원문 — 7. 제약 사항

**C1. AI API 사용 범위**

- **C1-1** — AI API Key는 **환경변수로만 관리**하며 **코드에 하드코딩하지 않는다.**
- **C1-2** — 과도한 비용 발생을 방지하기 위해, **1회 실행 시 요청 횟수는 1~2회 이내로 제한**하는 것을 **권장**한다.
- **C1-3** — **(권장 구현)** `commit` / `pr` 명령은 **각각 AI API 1회 호출**로 결과를 생성하고, **로그에 호출 횟수를 출력**한다.

**C2. Git 연동 범위**

- **C2-1** — Git 변경 사항 수집은 **`git status`, `git diff` 범위로 제한**한다.
- **C2-2** — 커밋/PR 생성은 **초안 텍스트 출력까지를 목표**로 한다.
- **C2-3** — 🚫 **`git push`, GitHub PR 생성(API 연동) 등 원격 저장소 자동 반영 기능은 구현하지 않는다.**

**C3. 보안/민감정보**

- **C3-1** — `git diff`에 포함될 수 있는 **민감정보(API Key, 개인정보 등)는 프롬프트에 포함하지 않도록 주의**한다.
- **C3-2** — 아래 중 **1개 이상**을 `-safe-mode` 같은 **옵션으로 제공**한다.
  - **(A)** diff에서 특정 패턴(API Key 형태, 이메일 등)을 **마스킹 후 전송**
  - **(B)** diff **일부만 전송**(예: **최대 10개 파일, 최대 200줄**)
- **C3-3** — **생성된 커밋/PR 문구는 최종 정답이 아니며, 사용자가 검토 후 적용한다.**

> 🚫 **특히 눈에 띄게 — 하지 말아야 할 것**
> - API Key 하드코딩 (C1-1)
> - `git push` / GitHub PR 자동 생성 / 원격 저장소 자동 반영 (C2-3) — **구현하면 안 된다. 범위 초과다.**
> - `git log`, `git show` 등으로 수집 범위 확장 (C2-1은 `git status`/`git diff`로 **제한**)
> - 한 번 실행에 AI API를 3회 이상 호출 (C1-2 권장 위반)
> - 웹 UI/GUI 제작 (개발 환경: 터미널 프로그램)

### 0.8 📚 이 과제가 공부하길 원하는 것 (학습 지도)

> (해설) 아래 표는 전부 해설이다. 각 행은 "요구사항 ID → 그 뒤에 숨은 개념 → 면접/평가에서 실제로 묻는 질문" 순서다. 평가 체크리스트(`ai_commit_pr_generator.md`)의 *핵심 개념 이해* / *확장 사고 및 트러블슈팅* 항목을 이 표에 녹였다.

| 요구사항 | 표면적으로 시키는 일 | 실제로 학습시키려는 개념 | 스스로 답해볼 질문 |
| --- | --- | --- | --- |
| **R1-2, R1-3** | `git status` / `git diff` 결과 가져오기 | **프로세스 간 통신 — `subprocess`로 외부 명령의 stdout을 프로그램 입력으로 연결**하기. `shell=True` 금지, 인자 리스트 전달, `returncode` 확인, 인코딩(UTF-8) 처리, staged(`--cached`) vs unstaged diff의 차이 | git 명령을 `os.system()`이 아니라 `subprocess.run(capture_output=True)`으로 부르는 이유는? `git diff`와 `git diff --cached`는 무엇이 다르며 내 도구는 어느 쪽을 봐야 하나? |
| **R1-1** | "프로젝트 루트에서 실행" | **실행 컨텍스트 검증(precondition check)**. `git rev-parse --is-inside-work-tree` / `--show-toplevel` 로 여기가 Git 저장소인지 먼저 확인하고 아니면 친절히 실패하기 | Git 저장소가 아닌 폴더에서 실행하면 내 프로그램은 어떤 메시지를 내고 몇 번 종료 코드로 끝나나? |
| **R1-4** | 변경 없으면 메시지 출력하고 종료 | **Guard clause / early return, 그리고 "돈이 드는 호출을 하기 전에 가드를 둔다"는 비용 설계**. 빈 diff는 에러가 아니라 정상 종료 경로다 | 변경이 없을 때 종료 코드는 0인가 1인가? 왜? 이 가드가 없으면 실행 1회에 얼마가 낭비되나? |
| **R2-1, C1-1** | API Key를 환경변수로 | **시크릿 관리(secret management)** — 소스코드와 자격증명의 분리, `os.environ` / `.env`(그리고 `.gitignore`), 키가 커밋되었을 때 히스토리에 영구히 남는다는 사실 | 키를 코드에 넣고 커밋했다가 지우는 커밋을 하면 왜 소용이 없나? `.env`는 왜 반드시 `.gitignore`에 들어가야 하나? |
| **R2-2** | API 호출해서 결과 출력 | **REST API 클라이언트 구성** — 엔드포인트/헤더(Authorization)/JSON 바디/타임아웃, 그리고 응답 JSON에서 생성 텍스트를 파싱해 꺼내는 경로. 과제 목표 1의 "요청 구성 → 응답 처리 → 예외 대응" 전체 흐름 | 요청 바디에 들어가는 필드를 전부 말할 수 있나? 응답 JSON의 어느 경로에서 텍스트를 꺼내나? 타임아웃을 안 걸면 무슨 일이 생기나? |
| **R2-3** | 호출 실패 시 원인 포함 메시지 | **예외 분류와 사용자 친화적 에러 메시지**. 인증 실패(401) / 레이트리밋(429) / 네트워크 타임아웃 / 5xx 를 구분해 각기 다른 안내를 준다. 스택트레이스를 그대로 토해내지 않기 | 401과 429에 대해 사용자에게 서로 다른 안내를 주고 있나? 재시도(backoff)를 넣어야 하는 에러는 어느 것인가? |
| **R2-4** | 파라미터를 CLI 옵션으로 | **CLI 설계(argparse 서브커맨드 + 기본값)와 "실험 가능성"**. 파라미터를 하드코딩하면 값을 바꿔볼 때마다 코드를 고쳐야 한다 → 재현성/실험 용이성. 체크리스트 2-3번 항목이 정확히 이것을 묻는다 | `--temperature 0`과 `--temperature 1.2`로 같은 diff를 넣었을 때 출력 차이를 **재현해서 보여줄 수 있나**? 기본값을 그 숫자로 정한 근거는? |

### 0.9 자주 놓치는 함정

> (해설) 명세를 빠르게 훑으면 놓치기 쉬운 조건들이다.

1. **"50자"와 "72자"는 서로 다른 규칙이다.** R5-2는 *50자 이내 **권장**, **최대** 72자*다. 50자를 하드 제한으로 구현하면 원문과 다른 동작이고, 72자만 보면 권장선을 잃는다. **권장 초과 시 경고, 상한 초과 시 실제 절삭/재생성**처럼 두 단계로 구분해야 원문 그대로다. (PR 제목은 단일 상한 80자.)

2. **R1-4는 "출력하고 **종료**"다 — AI API를 부르면 안 된다.** 변경 사항이 없는데도 API를 호출한 뒤 "변경 없음"을 출력하면 요구사항 위반이자 비용 낭비다. 가드는 **API 호출 앞**에 있어야 한다.

3. **R3-4/R3-5의 조건부 구조.** 커밋 본문은 **선택**이다. 하지만 "본문을 포함하는 경우에는" 최소 기준(파일 1~3개 언급 **또는** 핵심 변경 1~2개 불릿)을 반드시 만족해야 한다. 본문을 넣기로 했다면 이 기준의 검증까지 구현해야 완결이다. 반면 **커밋 제목 1줄은 무조건 필수(R3-3)**.

4. **R5-1은 "택1"이다 — 둘 다 하라는 게 아니다.** *"검증 후 재생성 **또는** 후처리 중 택1"*. 어느 쪽을 골랐는지, **왜 골랐는지**를 설명할 수 있어야 한다(평가 체크리스트 3-4번이 정확히 이걸 묻는다). 재생성을 골랐다면 C1-2("1회 실행 시 1~2회 이내 권장")와 충돌하지 않도록 재시도 상한을 둬야 한다.

5. **`git push` / GitHub PR 자동 생성은 "안 하는 것"이 요구사항이다(C2-3).** 열심히 구현하면 가산점이 아니라 범위 위반이다. 수집 범위도 `git status`/`git diff`로 **제한**되어 있다(C2-1) — `git log`로 커밋 히스토리를 긁어오는 것도 범위 밖이다.

6. **safe-mode는 "있으면 좋은 것"이 아니라 제약 사항의 필수 항목이다(C3-2).** (A) 마스킹 **또는** (B) 일부만 전송(예: 최대 10개 파일, 최대 200줄) 중 **최소 1개**를 옵션으로 제공해야 한다. "주의한다"는 문장(C3-1)만 README에 적고 코드가 없으면 미충족이다. 숫자 예시(10개 파일 / 200줄)도 그대로 기록해 두자.

7. **R2-4의 "기본값을 둔다"를 흘리기 쉽다.** 옵션만 만들어 두고 값을 반드시 입력해야 실행되면 안 된다. 옵션 없이 실행해도 동작해야 하고, 그 기본값을 왜 그 숫자로 정했는지 설명할 수 있어야 한다.

8. **R6-3의 "1개 이상 포함"은 README 요구다.** 민감정보 대응 **또는** 비용/요청 횟수 제한 중 하나 이상을 **문서에** 써야 한다. 코드에만 구현하고 README에 안 적으면 R6-3 미충족이다.

9. **C1-3의 "호출 횟수를 로그에 출력"은 권장 구현이지만 증빙에 강력하다.** `[INFO] AI API 호출 1회` 같은 한 줄이 "비용을 인지하고 설계했다"는 가장 값싼 증거다.

#### 🔍 발견된 격차와 보완 제안

- **G1 (중요) — 커밋 히스토리·브랜치 작업 흐름이 없다.** 최종 산출물 2는 "커밋 히스토리와 브랜치 작업 흐름을 확인할 수 있다"를 요구하는데, 저장소는 커밋 1개(`44bef2f init: Git 변경 사항 기반 커밋·PR 초안 생성 CLI`), 브랜치 `master` 단독이다.
  → 보완: 남은 작업(예: R5-2 경고 추가)을 `feature/...` 브랜치에서 수행하고, **이 도구로 커밋 메시지와 PR 초안을 생성해** 커밋/PR 을 만들면 G1 과 B1 을 한 번에 해소한다.

- **G2 (중요) — 실제 AI API 호출 화면이 저장소에 없다.** `docs/samples/01~05` 는 전부 `--dry-run` 캡처라 `API 호출 0회` 로 찍혀 있고, `README.md:629-161` 의 출력 예시는 직접 작성한 것(본인도 "형식을 보여주기 위한 예시"라고 명시, `README.md:669`)이다. 제출 증거 체크리스트 1번("단일 실행으로 … AI API 호출 … 끝까지 동작하는 화면")을 문자 그대로 만족시키는 자료가 없다.
  → 보완: `bash demo.sh --live` 를 1회 실행해 `01_commit.txt`/`02_pr.txt` 를 실호출 결과로 교체하거나, 별도로 `docs/samples/00_live.txt` 를 추가한다(`demo.sh:80-84` 에 이미 `--live` 경로가 있다).

- **G3 (경미) — R5-2 의 "50자 권장" 이 실행 단계에서 사라진다.** `title_recommended`(50)는 프롬프트에만 쓰이고(`aigitgen/prompts.py:100,174`), 검증기는 72자만 본다(`aigitgen/polish.py:150-151`). 66자 제목이 아무 경고 없이 통과하는 것을 확인했다. 명세는 "50자 이내 권장(최대 72자)"로 **두 숫자를 구분**한다.
  → 보완: `validate_commit()` 은 그대로 두고(재생성 트리거는 72자 유지), `polish_commit()` 뒤에 `len(title) > c.title_recommended` 면 `render.warn("제목이 N자입니다 — 권장 50자를 넘었습니다")` 한 줄을 추가하면 5줄 이내로 해결된다. 권장 초과=경고, 상한 초과=절삭의 2단계가 된다.

- **G4 (경미) — B2-1 의 "기존 스타일 분석" 근거가 없다.** `.ai-gitgen.json` 의 `team` 컨벤션은 합리적이지만 어떤 저장소의 어떤 커밋들을 보고 도출했는지가 없다.
  → 보완: README §7 앞에 "대상 저장소 `codyssey_BX-Y` 의 최근 커밋 N개 중 feat/fix/docs 가 M% … 그래서 prefix 를 6종으로 제한했다" 식의 3~5줄 분석 근거를 붙인다.

- **G5 (경미) — 문서 내 숫자/코드 불일치.** `docs/설계_노트.md:271` 은 "86개 테스트 중 8개", `README.md:853` 은 "95개 테스트" 라고 적는다(실제 95개). 또 `docs/설계_노트.md:22-23` 의 예시 코드는 `kwargs["temperature"] = ...` 인데 실제 구현은 `extra_body` 를 쓴다(같은 문서 97-113 줄에서 설명하는 방식). `docs/설계_노트.md:231` 의 `len(ctx.files)` 도 실제로는 `ctx.relevant_files`(`aigitgen/polish.py:325`)다.
  → 보완: 세 곳의 숫자·식별자를 실제 코드에 맞춘다.

- **G6 (참고) — 로그와 산출물이 같은 stdout 으로 나간다.** `aigitgen/render.py:20-38` 에서 `[INFO]/[WARN]/[DONE]` 이 stdout 으로 나가므로 `python main.py commit > msg.txt` 가 로그까지 담는다. 요구사항 위반은 아니지만(R5-5 는 구획 분리만 요구), 명세 0.8 의 학습 질문("`git commit -F -` 에 파이프할 수 있나")에 대한 답을 만들려면 로그를 stderr 로 보내면 된다.

## 5. 민감정보 대응 — 안전 모드

`git diff` 에는 API Key, 토큰, 이메일이 섞여 들어갈 수 있다.
그대로 프롬프트에 넣으면 **외부 서비스로 비밀이 나간다.** 그래서 안전 모드가 **기본값으로 켜져** 있고,
두 가지 대응을 **모두** 적용한다.

**(A) 마스킹** — 정규표현식으로 찾아 `«MASKED:...»` 로 치환한다.

| 규칙 | 대상 |
| --- | --- |
| `private-key-block` | `-----BEGIN ... PRIVATE KEY-----` 블록 전체 |
| `anthropic-key` / `openai-key` | `sk-ant-...` / `sk-...` |
| `github-token` | `ghp_` `gho_` `ghu_` `ghs_` `ghr_` |
| `aws-access-key` | `AKIA...` / `ASIA...` |
| `google-api-key`, `slack-token`, `jwt`, `bearer` | 각 공급자 토큰 형태 |
| `assignment` | `password = "..."`, `SECRET: '...'` 같은 대입문의 **값** |
| `email`, `kr-rrn` | 이메일 주소, 주민등록번호 형태 |

**(B) 전송량 제한** — 기본 **최대 10개 파일 / 200줄**. 초과분은 잘라내고 생략 사실을 프롬프트에 적는다.
비용을 줄이는 동시에, 관련 없는 파일이 통째로 나가는 것을 막는다.

순서는 **마스킹 → 잘라내기** 다. 반대로 하면 잘려나간 구간의 비밀은 검사조차 되지 않는다.
([`redact.apply()`](aigitgen/redact.py) 의 주석과 `test_마스킹이_잘라내기보다_먼저_일어난다` 가 이 순서를 고정한다.)

### ON/OFF 결과 차이 (보너스 3 증빙)

같은 변경에 대해 `--show-prompt` 로 전송 페이로드를 찍어 비교한 것이다.

```diff
  [INFO] 안전 모드 ON — 마스킹 2건 · 파일 3/3개 · 줄 69/69줄 · 규칙별(anthropic-key×1, email×1)
  [INFO] 안전 모드 OFF — diff 를 가공하지 않고 그대로 전송합니다.

- +PG_API_KEY = "«MASKED:ANTHROPIC_KEY»"      ← 안전 모드 ON
- +SUPPORT_EMAIL = "«MASKED:EMAIL»"
+ +PG_API_KEY = "sk-ant-api03-EXAMPLE-NOT-A-REAL-KEY-000000"   ← 안전 모드 OFF
+ +SUPPORT_EMAIL = "billing@example.com"
```

전문: [04_safemode_on.txt](docs/samples/04_safemode_on.txt) ↔ [05_safemode_off.txt](docs/samples/05_safemode_off.txt)

**한계.** 정규표현식은 아는 형태만 잡는다. 사내 전용 토큰 형식은 `.ai-gitgen.json` 의
`safe_mode.extra_patterns` 에 직접 등록해야 한다(7절). 안전 모드는 **마지막 방어선이 아니라 안전망**이고,
애초에 비밀을 커밋하지 않는 것이 먼저다.

## 6. 비용과 요청 횟수

| 항목 | 값 |
| --- | --- |
| 한 번 실행의 API 호출 | **1회** (형식 위반 시 재생성 포함 최대 **2회**) |
| 호출 횟수 표시 | `[DONE] ... — API 호출 N회, 토큰 입력 x / 출력 y` 로 매번 출력 |
| 기본 `max_tokens` | 2000 |
| 전송 diff 상한 | 10개 파일 / 200줄 (안전 모드 ON 기준) |

호출 상한은 [`cli.MAX_API_CALLS`](aigitgen/cli.py) 에 상수로 박혀 있다. 재생성은 최대 1번이므로
`--no-retry` 를 쓰지 않아도 2회를 넘지 않는다.

**권장 사용법**

- 커밋 직전 한 번만 돌린다. 결과가 마음에 안 들면 `--temperature` 를 올려 **한 번 더** 돌리는 정도로 끝낸다.
- 거대한 변경은 먼저 커밋을 쪼갠다. diff 가 크면 비용도 늘고 요약 품질도 떨어진다.
- 형식만 확인하고 싶을 때는 `--dry-run` 을 쓴다. **비용이 0원**이다.
- `--max-diff-lines` 를 낮추면 입력 토큰이 곧바로 줄어든다.

## 7. 팀 컨벤션 커스터마이징 (보너스 2)

**대상 저장소 루트**에 `.ai-gitgen.json` 을 두면 커밋/PR 규칙을 바꿀 수 있다.
(이 저장소의 [`.ai-gitgen.json`](.ai-gitgen.json) 이 그대로 예시다.)

```json
{
  "safe_mode": {
    "max_files": 10,
    "max_diff_lines": 200,
    "extra_patterns": [["사내-사번", "EMP-\\d{6}", "«MASKED:EMP»"]]
  },
  "conventions": {
    "team": {
      "commit": { "prefixes": ["feat", "fix", "docs"], "scope": "required", "title_max": 72 },
      "pr": {
        "extra_sections": ["Risk"],
        "min_bullets": 2,
        "checklist": ["로컬 테스트 통과", "문서 갱신 확인", "민감정보 미포함 확인"]
      }
    }
  }
}
```

| 키 | 효과 |
| --- | --- |
| `commit.prefixes` | 허용 커밋 타입. 목록 밖 타입은 검증에서 걸리고 후처리로 교체된다 |
| `commit.scope` | `required` / `optional` / `none` |
| `commit.body` | `required` / `optional` / `none`. `none` 이면 본문을 지우고, `required` 면 비었을 때 Git 사실로 채운다 |
| `commit.title_recommended`, `title_max` | 제목 길이 규칙. 프롬프트와 검증기가 같은 숫자를 쓴다 |
| `pr.extra_sections` | Why/What/How to Test **뒤에** 붙는 섹션 |
| `pr.min_bullets` | 섹션당 최소 불릿 수 |
| `pr.checklist` | 본문 끝에 `- [ ]` 체크리스트로 붙는다 |
| `pr.tone` | 프롬프트에 그대로 전달되는 문체 지시 |
| `safe_mode.*` | 안전 모드 숫자 정책과 추가 마스킹 규칙 (보너스 3) |

> **Why/What/How to Test 는 컨벤션으로도 못 없앤다.** 과제가 요구한 필수 섹션이라
> `extra_sections` 에 이 셋을 적으면 설정 오류로 거부한다.
> `default_convention` 키로 `--convention` 없이도 기본 적용되게 할 수 있다.

### 적용 전 / 후 비교 (보너스 2 증빙)

| | 기본 (`python main.py pr`) | 팀 컨벤션 (`--convention team`) |
| --- | --- | --- |
| 섹션 | Why / What / How to Test | Why / What / How to Test / **Risk** |
| 섹션당 불릿 | 최소 1개 | 최소 **2개** |
| 체크리스트 | 없음 | **3개 항목** 자동 부착 |
| 커밋 스코프 | 선택 | **필수** (`feat(payment): ...`) |
| 마스킹 규칙 | 기본 12종 | 기본 12종 + **사번 / 슬랙 웹훅** |

## 9. 테스트

```bash
python -m unittest discover -s tests -t tests -v
```

95개 테스트가 **네트워크도 API Key 도 없이** 2초 안에 끝난다.
AI 호출은 [`tests/helpers.py`](tests/helpers.py) 의 `FakeGenerator` 로 갈아끼우고,
Git 은 매번 임시 저장소를 새로 만들어 쓴다.

`anthropic` 이 설치돼 있으면 [`tests/test_client_wire.py`](tests/test_client_wire.py) 8건이 더 돈다.
로컬 HTTP 서버를 띄우고 `base_url` 을 그쪽으로 돌려 **실제로 전송되는 JSON 본문**을 받아 검사한다
(모델·`max_tokens`·스키마가 실렸는지, `temperature` 가 들어갔는지/빠졌는지, 401·500·연결 실패가
어떤 안내로 번역되는지). SDK 가 없으면 이 8건만 건너뛴다.

과제 제약은 서술이 아니라 **AST 검사**로 고정했다 (`tests/test_cli.py` 의 `TestConstraints`).

- 실행하는 git 하위 명령이 `rev-parse` / `status` / `diff` / `symbolic-ref` 로 제한되는가 → `git push` 는 호출 자체가 불가능
- `requests` / `urllib` / `socket` 을 직접 임포트하지 않는가 → 네트워크는 공식 SDK 로만
- 소스에 API Key 형태 문자열이 없는가
- `subprocess` 를 `gitctx.py` 밖에서 쓰지 않는가

## 10. 하지 않는 것

과제 제약에 따라 **원격 저장소를 건드리지 않는다.**

- `git push` 하지 않는다
- GitHub PR 을 API 로 만들지 않는다
- 커밋을 대신 실행하지 않는다 — 출력된 텍스트를 사용자가 **직접 검토하고** 적용한다

Git 수집 범위도 `git status` / `git diff` 로 한정한다.
추적되지 않은(untracked) 파일은 **이름만** 프롬프트에 넣고 내용은 넣지 않는다.
